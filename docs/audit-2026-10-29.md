## Prioritized findings

### High — extreme simulation-time overflow escaped the engine

`ScheduleOutput` and `ScheduleTimer` used checked addition for `_now + delayTicks`, which prevented wrapped timestamps but allowed `OverflowException` to escape from an ordinary simulation advance. A periodic waveform advanced to `long.MaxValue` reproduces the boundary. This is now hardened: event scheduling that exceeds the representable time range halts the run, clears queued work, and reports error `RAD102`. A focused regression test covers the behavior.

### Medium — deterministic single-driver conflict value is order-sensitive

`SingleDriverResolution` returns the first active driver's value and separately raises a conflict diagnostic. The compiler orders flattened pins deterministically, so identical authored projects are reproducible; however, reordering equivalent instances can change the apparent signal value. The diagnostic does not make that value safe to consume. This policy is documented and compatibility-sensitive; consider a future explicit invalid/unknown result channel that does not assume an `X` value exists in every domain.

### Medium — repository governance files are absent; Windows CI remains unverified

No `.github` workflow, license, contribution guide, or security reporting document was present at audit time. A Linux/Windows workflow has since been added, but it has not run on GitHub or Windows in this session. Licensing remains an owner decision; this audit makes no license selection.

### Medium — serializer atomicity is process-level, not proven crash durability

`ProjectSerializer.Save` writes a sibling temporary file and replaces the destination with `File.Move(..., overwrite: true)`, with cleanup in `finally`. Tests confirm replacement and no leftover temporary file in the normal path. They do not simulate process termination, power loss, filesystem-specific rename behavior, backup recovery, or write-through durability. Those guarantees need explicit platform-aware requirements and fault-injection tests before being claimed.

### Medium — hierarchy depth is capped at 64 without demonstrated need

The compiler recursively expands reusable definitions and rejects depth above 64. This is a useful stack/resource guard, and shipped examples are shallower. The current limit's practical necessity and failure message are not stress-tested at boundary depths. Raising or removing it without iterative expansion and resource controls could trade an explicit diagnostic for stack exhaustion.

### Low — benchmark evidence is workload-specific

`docs/benchmarks.md` records roughly 9–12 million events/second on a synthetic zero-delay inverter chain, measured on a Ryzen 9 9950X3D. The 2,000-gate case was reproduced above, but this is still not broad performance evidence and does not characterize memory-heavy, simultaneous-event, trace-heavy, or editor workloads.

## Unverified claims and test gaps

- Equivalent circuits under component insertion reordering and hierarchy flattening are not shown to have broad metamorphic coverage. Existing determinism tests mostly compare repeated compilation/runs of the same authored ordering.
- Simultaneous event FIFO behavior is described in code and exercised indirectly, but a comprehensive public semantic contract for cancellation, inertial delay, setup/hold, and simultaneous state changes is absent. Current primitive delays are transport delays; physical setup/hold behavior is not modeled.
- The convergence guard is per component per timestamp. It detects repeated zero-delay evaluation but is not a general bound on total events, total simulated work, or long-running periodic sources. Cancellation is available on `AdvanceTo`, but ordinary CLI runs have no event budget.
- Atomic save tests cover the successful path, not fault injection or preservation of an earlier file when a write/replace fails.
- Editor unit/rendering tests are headless, but interactive accessibility, large-project usability, and input routing remain manual checks.
- No independent electrical or photonic physical model exists; digital timing ticks are abstract and must not be interpreted as physical time.

## Architectural and performance risks

- The event queue, compiler, net resolver, and primitive runtime are compact and understandable. The current simulator allocates one event per transition and uses one global heap; large fanout, high activity, trace storage, or many equal-time events may dominate before raw per-event cost does.
- Compilation flattens hierarchy recursively and uses union-find. Source paths are retained for compiled components and representative nets, but merged authored nets necessarily collapse to one representative display identity; richer multi-origin provenance may be needed for diagnostic explanations.
- Discrete signal domains and numeric display formats are deliberately separate. Future analog values need a different numerical representation and solver lifecycle rather than stretching integer signal indices.
- The editor and CLI both use `Radix.Core`; Core project references do not include Avalonia. This is the right headless boundary and should remain enforced by CI.

## Future solver direction

Keep the current event engine as a discrete solver. Add a solver-neutral circuit model only when requirements are concrete, then implement an analog subsystem around modified nodal analysis (MNA): node voltages and branch currents, sparse conductance/Jacobian assembly, nonlinear device stamping, Newton iteration with tolerances and convergence diagnostics, and transient integration with adaptive timestep control. Model resistors, capacitors, inductors, independent sources, diodes, and transistor compact models explicitly; report model scope, temperature assumptions, tolerances, and failure to converge. Couple digital/analog boundaries through explicit threshold, drive impedance, hysteresis, and event-crossing rules rather than silently converting arbitrary values.

Treat photonics as separate solver families. Ray/geometric optics, frequency-domain wave optics, time-domain Maxwell solvers (such as FDTD), and photon-counting/quantum models answer different questions and have distinct cost and validity limits. Start with a documented model boundary and small analytic benchmarks for one regime; do not market ray tracing as wave propagation or classical fields as single-photon quantum behavior.
